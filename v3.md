## 📊 Key Design Decisions

1. **ClusterOnly Mode First**
   - Why: Simplest, proves architecture works
   - Result: Baseline for all comparisons

2. **RandomCluster Scheduler First**
   - Why: Minimal complexity, control group
   - Result: Shows value of sophisticated schedulers

3. **Real K8s, Fake Nodes (KWOK)**
   - Why: Authentic API behavior without resource overhead
   - Result: Realistic testing at low cost

4. **Optimistic Concurrency**
   - Why: Global consistency is impossible
   - Result: Fast decisions with conflict detection

5. **Three Placement Modes**
   - Why: Progressive sophistication
   - Result: ClusterOnly → NodePlacement → Gang

## 🎨 Architecture at a Glance

```
Scenario → Simulator → Scheduler → Kubernetes → Metrics
           (testbed)   (strategy)  (reality)    (results)
```

**Simulator** = Neutral testbed that enforces decisions  
**Scheduler** = Pluggable algorithm that makes decisions  
**Kubernetes** = Real clusters that run workloads  
**Metrics** = Utilization, fragmentation, latency data  

**Key Insight**: By separating testbed from strategy, you can swap schedulers and compare results objectively.

## 🐛 Troubleshooting

**Clusters won't start**: Check Docker is running, recreate with `make teardown && make setup`  
**KWOK nodes missing**: Run `./scripts/create-kwok-nodes.sh`  
**API returns 409**: State changed, scheduler will retry automatically  
**Pods not scheduling**: Check KWOK controller is running in each cluster  
**Go dependencies fail**: Run `go mod tidy`  

Full troubleshooting guide in **Quick Start Guide**.

## Key Design Principles

These principles are embedded throughout the design:

1. **Separation of Concerns**
   - Simulator = testbed (neutral, deterministic)
   - Scheduler = strategy (pluggable, comparable)

2. **Real K8s Behavior**
   - Actual API servers (Kind)
   - Realistic nodes (KWOK)
   - Real schedulers (default K8s)

3. **Observable Everything**
   - Metrics at every layer
   - Structured logs
   - Decision audit trail

4. **Start Simple, Scale Up**
   - Phase 1: RandomCluster + ClusterOnly (baseline)
   - Phase 2: Greedy + comparison
   - Phase 3: Advanced modes + failure injection

5. **Apples-to-Apples**
   - Same scenarios
   - Same clusters
   - Same workloads
   - Only scheduler changes

## Technical Highlights

### Why This Design Works

**Problem**: How do you test if a global scheduler is better than independent clusters?

**Solution**: Build a controlled testbed where:
- Same workloads run through different schedulers
- Outcomes are measured identically
- Environment is deterministic and reproducible

**Innovation**: Three placement modes (ClusterOnly → NodePlacement → Gang) let you progressively increase sophistication while maintaining valid comparisons.

**Result**: You can answer "Is this scheduler better?" with data, not opinions.
